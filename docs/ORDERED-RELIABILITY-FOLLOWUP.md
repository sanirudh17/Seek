## 1. Content-search retry

Previously every extraction error immediately incremented unreadable, with no automatic retry and no file-level UI list. Supported PDF and DOCX failures now go to the end of a finite queue. Every candidate gets its first attempt before any retry. The existing source/scope/secret/size checks and per-attempt deadlines apply again on retry; successful retries can populate the document cache. Only a failed second attempt becomes unreadable. Other read/enumeration errors remain explicit. A new query or cancellation stops the queue and does not classify unattempted retries as unreadable.

Progress retains the unique-file denominator, shows pending retries, and reports retries/recoveries. **Unreadable files (N)** opens a native GPUI dialog with full paths, final errors and attempt counts. The list belongs to the current query, is cleared on a new search and never includes recovered documents. The diagnostic report separately records first failures, retries, recoveries and final failures.

Nine content Rust checks pass, including deterministic transient recovery, permanent failure, exact retry order, no third attempt, and cancellation. Native desktop fixtures show three expected matches with two broken documents; the new list names both broken files and their final errors after two attempts. Strict all-target/all-feature Clippy and the optimized build are checked. The repeated real-folder release measurements are recorded in [the summary](benchmarks/content-retry-summary.json); path-bearing reports stay local under `.references`.

Reproduce the real read-only comparison with `python scripts/check-content-retry.py`. It resolves the current account's Known Folders, performs three separate **uncached** release scans for `note`, verifies 150 identical final paths with no duplicates, and reports first-attempt failures separately from final unreadable files. No normal app profile is initialized by this diagnostic.

Real release results: **150 identical matches in all three runs**, 437/437 candidates. First results **769.426 / 378.421 / 334.396 ms**, finished **44.112 / 25.355 / 23.346 s**. **2/366 documents failed their first attempt per run; 6/1,098 (0.546%) overall.** Every failure was one of the same two persistently unreadable PDFs. All six retries failed; no transient real-folder failure occurred during these samples. Recovery is verified with the deterministic owned test, not claimed from a real recovery that was not observed. Each final failure is named in the new UI. The old four additional transient PDF failures did not recur.

Release SHA256: `3DDF92DA8ABEB129E32CB9A11AFF2F953C3844D0BAB200F48914C29319FB9535`. The first new-executable scan was slower than the subsequent two; these are single-run samples, not a percentile or cold-cache guarantee. The known two unreadable PDFs remain a limitation.

## 4. Inaccessible-location and catch-up diagnostics

`Status.skipped` counts unique internal paths in the index's error map, restricted to the configured roots. It is not a count of skipped files, a per-session sum, or the Content search skipped count. Entries can come from failed directory enumeration, helper directory-access checks and failed filesystem watchers. The last Windows error is stored per path; successful enumeration clears that path's entry. Helper-backed saved indexes preserve the recorded map across launches, so the displayed number need not describe only this launch's failures. It also includes unavailable/deleted paths when Windows returns path-not-found, rather than only access-denied folders. The existing tooltip incorrectly described every error as a permission denial; it now explains these distinctions.

The current account's installed helper service is **Running / Automatic**. A normal **Auto** connection against a fresh, separate temporary full-C index actually completed as **ntfs + usn**, with no helper note, no fallback, no journal reset and no reconciliation. It is not enough to infer connectivity from service presence; this run received the MFT baseline and journal batches through the verified installed-service pipe. It indexed 3,453,656 entries / 323,417 directories and counted **221 unique locations**, all Windows error 5 (Access denied). Independent ordinary-user `std::fs::read_dir` calls failed on **all 221**. **Zero counted paths were readable, zero readable-path contents were missing in that comparison.** Most were protected ProgramData/Windows/system areas; this sample did not show a cloud-provider count explosion.

A single explicit walker comparison, also fresh and temporary, indexed 3,453,874 entries / 323,419 directories and counted **211 locations**: 209 access-denied and two path-not-found errors on a live changing drive. Independent directory enumeration failed on all 211; again zero counted paths were readable. The scans were sequential against a live drive, so their differing total entry counts are not a correctness comparison against one frozen snapshot. These diagnostic scans were debug builds; Auto catch-up was 59.487 s and walker 55.366 s. They are not release performance measurements and do not support a speed claim. Counts and timings are in [the sanitized summary](benchmarks/access-status-diagnostic.json). Private full path/error reports remain in owned temporary directories.

The screenshot's earlier **1,859** cannot be reproduced or attributed from the screenshot alone. Current Auto and walker counts are both near the earlier 190–215 range; the small current change is plausible on a changing system, whereas the large historical increase is **not explained by these measurements**. No evidence here establishes that it was caused by an absent helper, new cloud folders, or an indexing regression. The historical production profile/error map was deliberately not opened under the rule prohibiting real Seek data-folder tests. That historical attribution remains a stated limitation, rather than a claimed fix.

The misleading **0 folders checked** label was reproducible in the code and fresh whole-drive run: the UI used only `journal_directories` even while metadata/initial-index work and saving were in progress. Zero there means zero changed directories replayed so far, not zero folders indexed. Helper startup and checkpoint now publish their actual phase; without journal changes the status displays that phase rather than an unrelated zero. Nonzero journal counts are labelled **changed folders**. The inaccessible-path counting/indexing algorithm is unchanged; no reproducible readable-folder skip was found.

There is currently **no app UI to inspect the index's inaccessible-location paths**. None was added. The new Unreadable files dialog in item 1 concerns content-extraction failures only and is separate. The temporary diagnostic enumerated the recorded error map solely for this audit and compared it to the independent standard-library directory API; it is not a shipped feature. This verifies all counted paths at the observation time, not a frozen, whole-drive file-by-file correctness claim.
