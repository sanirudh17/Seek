# Item 1.2 — preview diagnostics and recovery

Implemented and checked on the worktree; not shipped. The multi-day production failure remains unreproduced, so this change does not assert a particular cause.

- Rotating `%LOCALAPPDATA%\Seek\logs\preview-host.log` (or the selected `--data` profile): 512 KiB request-boundary rotation, three backups, raw structured host stderr and structured parent results. Host error messages are capped. A bounded in-memory fallback reports an unwritable log. No document contents or filenames are intentionally logged, and nothing is uploaded.
- The first worker attempt has 15 seconds; normal attempts have four. One automatic retry is finite. Cancelled and mismatched-host work is not retried. The UI guard allows the new cold/retry budget and is cancelled on completion.
- App/host version and protocol fields are required in preview frames. New hosts also reject a wrong parent's version/protocol before document loading. Missing fields from old hosts produce a clear mismatch rather than an ambiguous unavailable state.
- The panel displays the actual error and offers keyboard-accessible Retry and Copy diagnostics. Error details scroll when long. Clearing cached frames cannot erase the retained diagnostic log.
- Hidden `seek.exe --preview-self-test --data <owned-profile> [--document-file <pdf-or-docx>]` prints stage/result timings without starting GPUI or indexing. With no file, it generates its own tiny PDF in the log directory. Native runtime/file stages and host process-entry estimates are in the log.

## Verification

77 regular app tests passed; three focused diagnostic checks were rerun after adding old-wire rejection. Strict all-target/all-feature Clippy and a normal debug build passed. Tests cover cold/normal budgets, exactly one retry, cancellation, version/protocol/missing-handshake rejection and bounded rotation preserving unrelated files. An actual spawned host rejected wrong version/protocol before reading the file. A broken-file self-test produced exactly two failed attempts with 15,000/4,000 ms budgets and the real Windows error.

20 desktop assertions passed in each theme: normal/enlarged PDF render, page turn, visible native error/actions, copying owned diagnostics to the clipboard, finite Retry failure, recovery to a valid selection and normal exit. The final human-readable error prefix was rechecked in Dark. [Native critique](1.2-CRITIQUE.md), [shape brief](1.2-PREVIEW-BRIEF.md). Production profiles and installed files were untouched.

Observed on the owned two-page digital fixture: **45 ms** process entry estimate, **232.6 ms** first preview, then **20.0 ms** normal / **57.3 ms** enlarged render in the reused host. This is the debug executable (**45,840,896 bytes**) with uncontrolled system caches, not painted UI or a release comparison. The published optimized baseline is **20,162,560 bytes**; its one-shot process+render samples are retained privately. Do not call the build-type difference a diagnostics size regression.

A dedicated host was considered but not added: the measured process entry was a minority of first render time on this fixture, and extraction currently couples to GPUI image/native thumbnail types. There is no evidence yet that splitting the executable would resolve the production incident. System cold-cache launch, antivirus/policy-induced stalls, actual multi-day recovery, physical HDR/mixed DPI and later high-contrast/glass changes remain unverified.
