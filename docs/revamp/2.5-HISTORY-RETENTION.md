# History retention and capacity safeguards

Phase 2.5 continuation in the isolated worktree, version 1.0.2. No publication or production-profile changes.

## Behavior

History offers **Archive and start fresh**, with an explanation that existing records are preserved while Undo and Put Back start fresh. The action runs on the owning worker and is disabled while requests are pending/loading or the current history has no jobs. Focus moves to the stable History control before rows disappear.

The view shows current journal usage and can reveal the previous history file in Explorer. All segments remain in the profile directory. Archived records are not reintroduced as active undo instructions. Nothing is automatically deleted or compacted. This is explicit archival retention, not automatic age-based deletion or a full in-app archive browser.

## File protocol

The original operations.jsonl remains the single-writer anchor. Its writer handle is retained across switches, alongside the current segment handle. Parent directories are held against replacement; bookkeeping files reject links, offline files and hard links.

Archiving creates a unique segment with a checksummed ArchiveBoundary containing the previous filename and highest job ID. That segment is flushed before a versioned current.json pointer is written to a unique temporary file, flushed and published using a same-directory MoveFileExW replacement with WRITE_THROUGH. No cross-volume copy or deferred reboot move is used. The in-memory writer switches only after publication succeeds. Archival never truncates or replaces an old segment.

Before the first pointer is published, the original journal receives one flushed SegmentedHistory format guard. Existing record bytes remain an exact prefix. Older builds reject the complete unknown event rather than appending to the former active journal. Later archived segments remain byte-for-byte unchanged. A 4 KiB marker allowance permits a legacy journal at its logical capacity to acquire this guard. Updated segmented profiles deliberately refuse older builds.

IDs continue increasing across boundaries. Checksums protect records within each segment; the manifest is not cryptographically authenticated. Startup validates the bounded pointer and filename, opens only the selected existing segment and refuses missing, damaged or traversing pointers. Unpublished segments are ignored and preserved. Existing incomplete-tail recovery applies to the active segment. No file operation is replayed.

A failed publication leaves the current writer usable and old records intact; an unpublished segment/temp pointer may remain as evidence. Deterministic boundary tests cover these states, without claiming physical power-cut verification.

## Capacity and validation

Before allowing Begin/Before, the journal reserves completion-record headroom within its nominal 32 MiB limit. Pending counts are maintained incrementally. An item that cannot fit with its completion allowance is refused before mutation; pending After records and final End retain their budget. This addresses the logical limit, not physical disk exhaustion. Native write failures still stop further mutations.
