# Guarded single-file move undo and redo

Phase 2.5 continuation. Native Windows, isolated worktree and owned test files; version remains 1.0.2. No publication.

## Result

Undo last operation and Redo last operation in History, File actions and Ctrl+K now choose the latest supported rename or single-file move. File-list Ctrl+Z/Ctrl+Shift+Z use the same route; editor undo stays scoped to the editor. Existing unsupported operations prevent skipping backward over them. Failed inverse attempts that changed nothing can be retried.

Before a Shell move, the operation worker captures the opened regular file's volume/file ID, length and primary-stream SHA-256. After completion it independently opens the Shell-reported destination without following a final reparse point. Only matching before/after fingerprints qualify. This excludes cross-volume moves and files changed during transfer; old journals without these fingerprints do not gain inferred undo eligibility.

Undo/redo reopens the exact current file, denies write/delete sharing, verifies its identity and content, and moves that handle without replacement. Source and destination parent chains stay open without delete sharing, and linked/offline parents are refused. Both parent scopes refresh after completion. Original parent absence, an existing destination, file modification or replacement leave the file untouched. A missing destination parent is not silently recreated.

This increment intentionally offers no partial inverse of a multi-item job: precisely one completed item outcome is required. It supports readable regular files up to 16 MiB on the same volume, with representable valid original filenames. Directory trees, copy undo, cross-volume move undo, Recycle Bin Put Back, broader redo and journal retention/reconciliation remain pending. Phase 2.5 is still partial.

## Native buffer correction

The restart/missing-parent test exposed a separate native path-buffer bug: FILE_RENAME_INFO had storage for the path bytes without always leaving a terminating zero WCHAR. Depending on alignment, Win32 DOS-path conversion could fail or resolve an unintended trailing path. Allocation now always reserves that terminator while FileNameLength excludes it. The destination parents remain anchored throughout the native call. A regression covers sixteen consecutive filename lengths, asserting the exact destination and preserved bytes.

Microsoft's FILE_RENAME_INFO contract describes the NUL-terminated FileName and no-replacement behavior: https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info.

## Verification

- Native worker integration: Shell move followed by undo and redo preserves the original file identity and bytes.
- Collision refuses overwrite, preserves both files, and permits retry after the conflicting item is removed.
- Modified files and replacement files with identical original bytes are refused.
- Move undo survives worker restart. Missing original parent refuses the inverse; restoring that parent allows retry.
- Multi-file and directory moves do not offer a partial undo.
- Sixteen path lengths verify exact native rename destinations and termination.
- Strict offline Clippy with warnings denied passed. Complete app suite: 130 passed, 4 ignored. Benchmark-feature debug build passed. No new GUI review launch was requested or performed for this increment; native worker tests exercised the filesystem operations themselves.
