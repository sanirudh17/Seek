# 2.5 - Operation journal and guarded rename checkpoint

Latest retention continuation: explicit archival, preserved segments, a persistent writer anchor, format guard, increasing IDs and reserved completion headroom. See [2.5-HISTORY-RETENTION.md](2.5-HISTORY-RETENTION.md) for the protocol, 143-test evidence and remaining scope.

Implemented locally; this is a partial phase. No version bump, push or release. No app launch for this pass, per the bundled-review instruction.

## Implemented

- Dedicated ordinary-user Windows operation STA remains in place, with Shell progress/error/cancel dialogs for copy, move, new folder and recycling. Clipboard and property-dialog requests are not file mutations and do not create undo records.
- The active profile contains operations.jsonl. Begin and per-item Before records are flushed before changes; After stores actual Windows outcomes and destinations, including the recycled item's parsing name when supplied; End distinguishes a completed job from an interrupted one. Native HRESULT success variants are classified explicitly. A failed per-item result cannot be promoted to an overall success solely because PerformOperations returned successfully.
- Records use a sequence/checksum chain and lossless UTF-16 path storage. One writer owns the history. Complete damaged records stop further mutations; an incomplete final write is preserved separately before the verified prefix is reopened. Startup never replays filesystem changes. Missing/unwritable history blocks a new mutation before it begins. Limits are 32 MiB per journal and 1 MiB per record; history rotation/recovery management remains pending.
- Operation history is available in File actions and Ctrl+K. It shows up to the latest 100 jobs, actual per-item destinations, failure/skip states and interrupted work. Escape restores stable browser focus instead of a disposed menu handle; Tab stays within the overlay. Unknown provider data stays unknown. New History UI has build/lint validation; native visual/accessibility acceptance is deferred to the next larger review.
- Rename uses the opened file object through SetFileInformationByHandle(FileRenameInfo), with ReplaceIfExists false. All parent directories are opened from root down and retained without delete sharing; linked/offline parents and source entries are rejected. This prevents a parent replacement during the operation. Collision checks occur in the native rename call, including a destination created after UI validation. File/folder and case-only renames are covered.
- Guarded rename undo/redo is exposed through File actions, History, the palette, and Ctrl+Z / Ctrl+Shift+Z while the file list has focus. Text editors retain their own undo. The inverse reopens the exact file object, denies concurrent write/delete, compares volume/file ID and the primary stream SHA-256 before renaming without replacement. Modified/replaced files and existing destinations are refused. History persists across restart; a failed collision can be retried after the conflicting item is handled.

## Bounds and remaining work

Undo/redo currently supports the latest eligible regular-file rename, with a readable primary stream up to 16 MiB and an original filename representable in the current text UI. Larger files, directory renames and unavailable snapshots remain ordinary rename operations with no undo claim. The snapshot does not authorize deleting copies or restoring arbitrary streams. A later completed mutation or an interrupted job prevents incorrectly undoing an older rename. File operations are disabled for undo while requests remain queued.

Move/copy undo, directory undo, Recycle Bin Put Back, full redo, durable history rotation/reconciliation controls and comprehensive conflict/progress acceptance are still required for full 2.5. The recycled parsing name is evidence, not a verified Put Back implementation. Batch rename (2.6) and New folder with selection depend on these remaining guarantees. Do not mark the phase or revamp complete.
